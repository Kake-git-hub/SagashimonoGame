# お化粧アプリ 実装計画

作成日: 2026-10-30
対象ブランチ: `ccr-7f507131-9308js`

このドキュメントは、あそびひろば（同じリポジトリ・同じ GitHub Pages）に、インカメラで顔を映しながら化粧を案内する新ゲーム「お化粧アプリ」を追加するための計画です。
このアプリは本来は単体のアプリ / Web サイトにしたいものですが、環境準備を省いて早く実機で確かめるため、まずはあそびひろばの中で試作します。
実装に入る前の合意用ドキュメントなので、気になる点はこのファイルにコメントするか、チャットで指摘してください。最後の「13. 壁打ち事項」に決めてほしいことをまとめてあります。

---

## 1. コンセプトと目的

**一言で**: インカメラに映した自分の顔の上に、顔認識で取った点群（478 点）をもとに「どこに・どの向きに」化粧するかを重ねて案内し、画面上で化粧を試せる「かしこい鏡」。

### 1.1 3 つの体験

| 体験 | 画面内の呼び名（案） | 内容 |
|---|---|---|
| 画面上で化粧してみる | ためす | リップ・チーク・アイシャドウなどを顔に重ねて描画。色と濃さを変えられる。ビフォー / アフター比較 |
| 化粧の手順を案内する | おしえて | 手順をステップで示し、顔の該当部分を光らせ、塗る向きを矢印で示す。顔が動いても追従する。実際の化粧をしながら見る前提 |
| 顔立ちから提案する | ていあん | 顔の形・目の形・肌の明るさから、チークの位置や眉の角度、おすすめの手順を提案する（ルールベース） |

### 1.2 この試作で確かめたいこと

1. iPad / iPhone の Safari とホーム画面 PWA で、カメラ ＋ 顔認識がリアルタイム（目標 15fps 以上）に動くか
2. ランドマークから唇・まぶた・頬などの領域を安定して切り出せるか（手やブラシで一部が隠れても破綻しないか）
3. 「領域を光らせて矢印で向きを示す」案内が、実際に化粧しながら見て役に立つか
4. 単体アプリに切り出せる構造（プラットフォーム非依存）で作れるか

### 1.3 試作の範囲外（将来）

- 商品（実在のコスメ）との連携、EC 連携
- 肌状態の分析（シミ・しわ等）
- AI（LLM）による自由文の提案・会話
- クラウド保存、SNS 共有、アカウント
- 塗れたかどうかの自動判定（塗る前との色差で判定する案はあるが後回し）
- WebGL による本格的な質感描画（3D のライティング付きリップ等）

## 2. 参考アプリ・技術の調査まとめ

### 2.1 参考アプリ

「バーチャルメイク」「AR メイク」ジャンル（YouCam メイク、ModiFace、各ブランドのバーチャルトライオン）の共通点は次の通りです。

- 鏡像表示のカメラ映像が画面の大部分を占め、下部にパーツタブ（リップ / アイ / チーク / 眉 …）と色パレット、濃さのスライダーが並ぶ
- ビフォー / アフターを左右分割やスライダーで比較できる。写真として保存できる
- チュートリアル型（資生堂の店頭「VIRTUAL HOW TO」に入っている YouCam チュートリアルなど）は、手順をステップで示しながら顔の該当部分をハイライトし、完成形を先に見せる
- 顔認識はすべて端末内で行い、カメラ映像をサーバーに送らないことを明示している

調査した主なページ:
- [バーチャルメイク・AR の活用事例まとめ（AIsmiley）](https://aismiley.co.jp/ai_news/virtual-makeup-ar/)
- [パーフェクト社 企業向けソリューション（YouCam）](https://www.perfectcorp.com/ja/business/solutions/enterprise)
- [資生堂 VIRTUAL HOW TO に YouCam チュートリアルを導入（パーフェクト社ニュース）](https://www.perfectcorp.com/ja/business/news/detail/1672)
- [EC でのバーチャルメイク（ECのミカタ）](https://ecnomikata.com/ecnews/22424/)
- [ModiFace の紹介（Mogura VR）](https://www.moguravr.com/?p=134704)

### 2.2 顔認識の技術

MediaPipe Face Landmarker（Web 版パッケージ `@mediapipe/tasks-vision`）が現在の標準的な選択肢です。

| 項目 | 内容 |
|---|---|
| 出力 | 顔ランドマーク 478 点（468 点 ＋ 両目の虹彩 10 点）、表情の係数 52 個（blendshapes: 笑い・目閉じ・口開けなど）、頭の位置と向きの 4×4 行列 |
| 実行 | WebAssembly ＋ WebGL（GPU）または CPU。モデルは端末内で動き、映像は外に出ない |
| パッケージ | `@mediapipe/tasks-vision` 1.2.0（Apache-2.0） |
| サイズ（実測） | JS バンドル 156KB、wasm ローダー JS 334KB、wasm 本体 14.5MB（SIMD 版）/ 12.9MB（非 SIMD 版）、モデル `face_landmarker.task` 3.76MB |
| 初回ダウンロード | 約 19MB（wasm 1 組 ＋ モデル）。2 回目以降はキャッシュから |

iOS まわりで見つかった注意点:

- ホーム画面に追加した Web アプリ（standalone）ではカメラ許可が保持されず、起動のたびに許可を聞かれることがある。WebKit の古くからの既知問題で、2024 年 9 月時点でも未解決の報告がある → [WebKit Bug 215884](https://bugs.webkit.org/show_bug.cgi?id=215884)、[Apple Developer Forums](https://developer.apple.com/forums/thread/788518)。Safari のタブで開けば許可は保持できる（サイトごとの設定で「許可」にできる）
- iOS Safari の GPU 実行で結果が壊れる報告がある（Face Landmarker ではなく ImageSegmenter の例）→ [mediapipe#6142](https://github.com/google-ai-edge/mediapipe/issues/6142)。GPU で異常があれば CPU に切り替えられるようにしておく
- Web Worker 内で OffscreenCanvas が使われない問題 → [mediapipe#5292](https://github.com/google/mediapipe/issues/5292)。試作ではメインスレッドで動かす

## 3. 仮決め事項（違っていれば指摘してください）

質疑をしていない点は、次の前提で進めます。すべて後から変更できます。

1. 名前は「おけしょう」、カードの絵文字は 💄、カードの色はピンク系
2. 本番（単体化後）の対象は「自分で化粧をする人」（大人・中高生）。試作の文言は、もどる・つぎへ等の共通ボタンはあそびひろばの調子（ひらがな）に合わせ、メイク用語（アイシャドウ・チーク・ハイライト等）はカタカナ・漢字をそのまま使う。文言は 1 ファイル（`strings.ts`）に集め、後で切り替えられるようにする
3. 縦持ちを基本にする。iPad 横持ちは映像を左、操作パネルを右に置いて崩れないようにする
4. 顔認識は `@mediapipe/tasks-vision` の Face Landmarker を使い、メインスレッドで動かす。GPU を既定にし、設定で CPU に切り替えられるようにする
5. 初回はオンライン必須（約 19MB のダウンロード、進捗を表示）。ダウンロード済みの端末ではオフラインでも動く（Service Worker の実行時キャッシュ）。あそびひろばのインストール時に全部事前キャッシュする方式は取らない（さがしものだけ遊ぶ端末にも 19MB 落とすことになるため）
6. メイクの描画は Canvas 2D（領域の塗りつぶし ＋ ぼかし ＋ 乗算合成）。WebGL（three.js）での質感描画は将来の拡張
7. 写真はアプリ内に保存しない。「ほぞん」は端末のダウンロード / 共有シート（iOS は「写真に保存」）に渡すだけ
8. べんきょうクイズの関門と年齢による難易度は使わない。プロフィールは保存キーの分離（`profileStorageKey`）にだけ使う
9. 効果音なし（既存ゲームに合わせる）
10. カメラ映像・ランドマーク・写真は端末の外に出さない。通信は wasm とモデルのダウンロードだけ。「はじめに」画面に明記する
11. 手順（レシピ）は最初に 2 種類（ナチュラル / おでかけ）＋ パーツごとの単発ガイド（リップだけ・チークだけ）を用意する。内容は一般的な手順で、専門家の監修は無い（画面にも「めやす」と書く）
12. 左右は「自分から見た左右」で表現する（鏡像表示なので画面上の左右と一致する）
13. 表示は常に鏡像（左右反転）。設定で反転なしにもできるが、ガイドの左右の文言は変えない

## 4. 体験の流れ

### 4.1 画面遷移

```
ホーム画面
 └─ 💄 おけしょう
     ├─ はじめに            カメラを使うことの説明・プライバシーの説明・「カメラをつかう」ボタン
     │    ├─ 許可された      → よみこみちゅう（顔認識の wasm / モデルのダウンロード進捗）→ ミラー画面
     │    ├─ 拒否された      → 「せっていで カメラを ゆるして」の案内 ＋「しゃしんで ためす」
     │    └─ カメラが無い    → しゃしんモード
     ├─ ミラー画面（メイン）  モード: ためす / おしえて / ていあん
     ├─ しゃしんモード        カメラの代わりに写真を選んで、同じ 3 モードを使う（PC での開発にも使う）
     └─ せってい             鏡像 / ガイドの濃さ / GPU・CPU / 点群の表示（デバッグ）
```

- 「もどる」でホームに戻るときは必ずカメラを止める（`track.stop()`）
- 画面が裏に回ったら（`visibilitychange`）カメラを止め、戻ってきたら再開する（iOS は裏で止まるため）
- 既存ゲームと同じく、画面が切り替わった直後のボタンは `useTapGuard` で約 1 秒押せないようにする

### 4.2 ミラー画面のレイアウト（縦持ち）

```
┌──────────────────────────────┐
│ ←  おけしょう             ⚙️ │  ヘッダー（env(safe-area-inset-top) 分の余白）
│  ✅ かおが みえています        │  状態（顔なし / くらい / とおい / よこむき を案内）
├──────────────────────────────┤
│                              │
│        カメラ映像（鏡像）    │  <video>（object-fit: cover）
│      ＋ メイク描画 <canvas>  │  ためす の塗り
│      ＋ ガイド描画 <canvas>  │  おしえて の領域と矢印、デバッグの点群
│                              │
├──────────────────────────────┤
│ [ためす] [おしえて] [ていあん] │  モードタブ
│ 💋リップ 🌸チーク 👁アイ ✏️まゆ ✨ハイライト │  パーツ（ためす）
│ ●●●●●●●●  つよさ ━━●━━       │  色パレットと濃さ
│ [くらべる] [ぜんぶけす] [📷]   │  ビフォー/アフター・リセット・保存
└──────────────────────────────┘
```

- おしえて モードの下部は「ステップ 3 / 10 チーク」＋ 一言の説明 ＋ [まえへ] [つぎへ]。ためす の塗りは消さず、手順の完成形として重ねて見せられる
- ていあん モードの下部は診断結果のカード（顔のかたち・目のかたち・おすすめ）と「このてじゅんで おしえて」ボタン
- iPad 横持ち（`@media (orientation: landscape)`）では映像を左 60%、操作パネルを右 40% に置く

## 5. 機能仕様

### 5.1 カメラ

- `getUserMedia({ video: { facingMode: 'user', width: { ideal: 1280 }, height: { ideal: 720 } }, audio: false })`
- `<video playsinline muted autoplay>`。表示は CSS `transform: scaleX(-1)` で鏡像。重ねる canvas も同じ CSS を当てる（座標変換を考えなくてよい）
- canvas の内部サイズは `video.videoWidth × videoHeight` に合わせ、CSS は video と同じ `object-fit: cover` にする。ランドマークは映像の正規化座標（0〜1）なので、そのまま掛けるだけで重なる
- 端末の向きが変わったら video のサイズを読み直す
- 顔認識に渡す映像は 640×480 程度に縮小した canvas にして負荷を抑える（表示は元の解像度）

### 5.2 顔認識

- `FaceLandmarker.createFromOptions(wasmFileset, { baseOptions: { modelAssetPath, delegate: 'GPU' }, runningMode: 'VIDEO', numFaces: 1, outputFaceBlendshapes: true, outputFacialTransformationMatrixes: true })`
- `requestAnimationFrame` ごとに `detectForVideo(frame, timestamp)`。推論時間を計測し、1 フレーム 50ms を超えたら 2 フレームに 1 回に間引く
- 点のブレ対策: 指数移動平均（係数 0.5 程度）で平滑化。顔が見つからなかったフレームが 0.5 秒続くまでは直前の結果を使い続ける（ブラシや手で一瞬隠れても描画が消えない）
- 頭の向き: 変換行列からヨー / ピッチ / ロールを求める。±20° を超えたら「まっすぐ むいてね」
- 表情: blendshapes の `mouthSmileLeft/Right` で「にっこり」を検出し、チークの位置（笑ったときの頬の高い所）を決めるのに使う。`eyeBlinkLeft/Right` でまばたき中はまぶたの領域を更新しない

### 5.3 顔のパーツ領域（`logic/landmarks.ts`）

ランドマークの番号から領域（多角形）を作る純粋関数群。tasks-vision が公開している接続リスト（`FaceLandmarker.FACE_LANDMARKS_LIPS` / `LEFT_EYE` / `LEFT_EYEBROW` / `FACE_OVAL` 等）を基本にし、チークなど独自の領域は番号の表で定義します。番号は MediaPipe の canonical face model のもので、下表は出発点（フェーズ 1 のデバッグ表示で番号を見ながら調整）です。

| 領域 | 使う点（概略） | 用途 |
|---|---|---|
| 唇（外側 / 内側） | 外 61,146,91,181,84,17,314,405,321,375,291,409,270,269,267,0,37,39,40,185 / 内 78,95,88,178,87,14,317,402,318,324,308,415,310,311,312,13,82,81,80,191 | リップ（外側 − 内側 を塗る） |
| 目（自分の右 / 左） | 右 33,7,163,144,145,153,154,155,133,173,157,158,159,160,161,246 / 左 263,249,390,373,374,380,381,382,362,398,384,385,386,387,388,466 | アイライン（上まつげの際）、目の形の判定、塗り除外 |
| まぶた（アイシャドウ） | 目の上縁 〜 眉の下縁 の間を補間して作る帯 | アイシャドウ（目尻側ほど濃く） |
| 眉（自分の右 / 左） | 右 70,63,105,66,107,55,65,52,53,46 / 左 300,293,334,296,336,285,295,282,283,276 | 眉のガイド、眉山の位置 |
| 頬（チーク） | 頬骨の高い点（自分の右 50 / 左 280 付近）を中心に、こめかみ（右 127 / 左 356 付近）へ向かう楕円 | チーク。「にっこり」時の位置を採用 |
| 鼻筋・顎先・頬骨の上 | 鼻 6→4、顎 152、頬骨 116 / 345 付近 | ハイライト |
| 目の下の三角 | 目の下縁 〜 頬の上 | コンシーラー |
| 顔の輪郭 | FACE_OVAL（10,338,…,152,…,109） | 顔の形の判定、ベースの範囲、明るさの計測範囲 |
| 虹彩（自分の右 / 左） | 468〜472 / 473〜477 | 黒目の中心（眉山の位置の基準）、目の大きさ |

左右は仮決め事項の通り「自分から見た左右」で書いています。MediaPipe の番号は若い方（33・70・50・127・468 など）が自分の右側で、鏡像表示では画面の右側に出ます。tasks-vision の定数名（`FACE_LANDMARKS_LEFT_EYE` = 263 系）はこれと一致するので、コード内の名前も「自分から見た左右」で統一します。

### 5.4 ためす（バーチャルメイク）

- レイヤー（下から順）: ベース（肌の均一化: 顔の輪郭内に薄い肌色を 10〜20% 重ねる）→ コンシーラー → チーク → アイシャドウ → アイライン → 眉 → ハイライト → リップ
- 描画（Canvas 2D）: 領域の多角形を塗り、ぼかし（`ctx.filter = 'blur()'`。iOS 17 以前は `ctx.filter` が無いので、レイヤーごとに別 canvas にして CSS の `filter: blur()` を当てる方式にする）、合成は色が乗るもの（リップ・チーク・アイシャドウ・眉）は `multiply`、明るくするもの（ハイライト・コンシーラー）は `soft-light`（無いブラウザは `lighter` を弱く）
- パレット: パーツごとに 8〜12 色（`public/makeup/palettes.json`）。「つよさ」は不透明度 0〜100%
- くらべる: 押している間だけメイク canvas を隠す（ビフォー）。左右分割も検討（フェーズ 2 で簡単な方を選ぶ）
- ぜんぶけす: レイヤーを空にする。パーツ単位の消しはタブの長押しかゴミ箱ボタン
- 重なり順と色は `logic/layers.ts` の状態（reducer）で持ち、描画はそれを読むだけにする（テストしやすくする）

### 5.5 おしえて（手順ガイド）

- レシピ（`public/makeup/recipes/*.json`、§6.1）のステップを順に表示する
- 各ステップで顔に重ねるもの
  - 領域: 点線の輪郭 ＋ 薄い塗り（ゆっくり明滅）
  - 矢印: 名前付きの点（例: 頬の高い所 → こめかみ）を結ぶ線に沿って矢印が 1.5 秒周期で流れる。両側にある部位は左右両方に出す
  - 補助の印: 眉山の位置（黒目の外側の垂直線）など、点や線で出す
- 条件付きの案内: `pose: 'smile'` のステップは「にっこり してみて」と出し、笑顔を検出したら頬の位置を確定する。`pose: 'closeEyes'` はアイシャドウで目を閉じて塗る場面に使う（目を閉じている間はまぶたの領域を最後に開いていたときの形で保持）
- 顔が見つからない / 横を向いている間はガイドを薄くし、状態欄で案内する
- 完成形を見たいときは、ためす の塗りをレシピの色で一括適用する「できあがりを みる」ボタンを置く
- 進み具合（塗れたか）の判定は試作ではしない。ユーザーが「つぎへ」を押す

### 5.6 ていあん（提案）

ルールベースで、ランドマークの比率から 3 つを出します。精度は「めやす」で、画面にもそう書きます。

| 判定 | 計算 | 提案に使うこと |
|---|---|---|
| 顔のかたち | 顔の縦（10→152）と横（234→454）の比、顎の角度（頬骨幅に対する顎幅） | 丸顔 / 面長 / 卵型 / ベース型 → チークの形（丸く / 斜めに）、ハイライト・シェーディングの位置 |
| 目のかたち | 目頭と目尻を結ぶ線の傾き（33→133、362→263）、目の縦横比 | つり目 / たれ目 / 標準 → アイラインの延長方向、アイシャドウの濃くする位置 |
| 目の大きさ | 目の高さと虹彩の直径の比 | アイラインの太さ、マスカラの強調 |
| 肌の明るさ・色味 | 頬の小領域の平均色（照明に左右されるので弱い根拠として扱う） | パレットの初期選択（明るめ / 落ち着いた色） |

出力: 診断カード（例: 「たまご型、すこし たれ目」）と、おすすめのレシピへのボタン、ためす の初期パレット。

### 5.7 状態チェック（状態欄に出す文言）

| 状態 | 判定 | 表示 |
|---|---|---|
| 顔なし | 0.5 秒以上検出なし | 「かおを うつしてね」 |
| 遠い | 顔の横幅が映像幅の 25% 未満 | 「もうすこし ちかづいてね」 |
| 近すぎ・はみ出し | 輪郭が映像の外 | 「すこし はなれてね」 |
| 暗い | 顔の輪郭内の平均輝度が閾値未満（64px に縮小した canvas で 0.5 秒ごとに計測） | 「もうすこし あかるいところで」 |
| 横向き | ヨー / ピッチ が ±20° 超 | 「まっすぐ むいてね」 |
| 推論が重い | 平均 100ms 超 | 設定で CPU / GPU の切替を案内（表示は控えめ） |

### 5.8 しゃしんモード

- `<input type="file" accept="image/*">` で写真を選び、`runningMode: 'IMAGE'` で 1 回だけ検出して同じ 3 モードを使う
- カメラが使えない端末・PC での開発・自動テストに使う。`?makeupdebug=1&photo=<url>` で起動直後にこのモードに入れるようにする（e2e 用）

### 5.9 保存・共有

- 📷 ボタンで、video の現在のフレーム ＋ メイク canvas を 1 枚の canvas に合成（鏡像のまま）し、`canvas.toBlob` → `navigator.share({ files })` が使えれば共有シート（iOS で「写真に保存」できる）、無ければ `<a download>`
- ガイドの矢印や点群は写真に入れない
- アプリ内には保存しない（IndexedDB に写真を貯めない）

### 5.10 せってい・デバッグ

- 鏡像 ON/OFF、ガイドの濃さ、GPU / CPU、点群の表示（番号つき: 領域の調整に使う）、FPS と推論時間の表示
- `?makeupdebug=1` で `window.__makeupDebug`（最新のランドマーク・状態・`setPhoto(url)`・`applyLook(id)`）を公開し、e2e から操作できるようにする（ネジはずしの `?nejidebug=1` と同じ考え方）

## 7. 技術選定

### 7.1 顔認識ライブラリの比較

| 候補 | 点数 | 初回 DL | 速さ（目安） | 備考 |
|---|---|---|---|---|
| **MediaPipe `@mediapipe/tasks-vision`**（採用案） | 478 ＋ 表情 52 ＋ 頭の行列 | 約 19MB | 速い（wasm SIMD ＋ GPU） | 現在の標準。iOS の注意点は §2.2 |
| TensorFlow.js `face-landmarks-detection`（tfjs ランタイム） | 468 / 478 | 約 4MB | 遅め | 表情・頭の行列なし。メンテ頻度が低い。DL サイズが問題になったときの代替 |
| face-api.js | 68 | 小 | 速い | 点が粗く、唇・まぶたの領域が作れない。不採用 |

ダウンロードサイズが大きい代わりに、唇・虹彩・表情・頭の向きまで取れる MediaPipe を採用します。サイズが受け入れられない場合だけ TensorFlow.js に落とす余地を残し、顔認識は `services/faceTracker.ts` の 1 ファイルに閉じ込めます。

### 7.2 配布の仕方（wasm とモデル）

- wasm ローダーと本体は `node_modules/@mediapipe/tasks-vision/wasm/` から Vite の `?url` import で取り込む（ビルド時にハッシュ付きで `dist/assets/` に出る。コピー用スクリプト不要、npm のバージョンと一致する）。`FilesetResolver.isSimdSupported()` で SIMD 版 / 非 SIMD 版を選び、`{ wasmLoaderPath, wasmBinaryPath }` を直接渡す
- モデル `face_landmarker.task`（3.76MB）は `public/makeup/models/` に置いてリポジトリにコミットする（ビルド時に Google のサーバーから取る方式は CI の外部依存になるため避ける）
- Service Worker: `.wasm` と `.task` は事前キャッシュに入れず（今の `globPatterns` にも含まれない）、`CacheFirst` の実行時キャッシュ `makeup-model` に入れる（§9.3）

### 7.3 描画

- フェーズ 2 は Canvas 2D。領域の塗り ＋ ぼかし ＋ 合成モードで、口紅・チーク・アイシャドウ程度なら十分それらしく見える
- 将来、質感（ツヤ・ラメ）を出したくなったら three.js（既に依存にある）で顔メッシュに UV を貼り、メイク用テクスチャを描く方式に移行する。描画層は `components/MakeupCanvas.tsx` に閉じ込め、入力（ランドマーク ＋ レイヤー状態）を同じにしておく

### 7.4 性能の方針（iPad / iPhone）

- 推論入力は 640×480、GPU 既定、1 フレーム 50ms 超で間引き
- 描画は推論と切り離し、表示の rAF では最新のランドマークで描くだけにする
- 平滑化（EMA）でブレを抑える
- FPS と推論時間を設定画面で見られるようにして、実機で数字を見ながら調整する

## 11. リスクと対策

| リスク | 対策 |
|---|---|
| ホーム画面 PWA でカメラ許可が保持されず毎回聞かれる（WebKit 既知問題） | 試作では許容し、フェーズ 0 で実態を確認。「はじめに」画面で許可の理由を説明。Safari のタブで開く運用も案内できるようにする。単体化時はネイティブ化で解決 |
| 初回ダウンロードが約 19MB | 進捗表示と Wi-Fi 推奨の文言。2 回目以降は実行時キャッシュ。あそびひろば全体の事前キャッシュには入れない |
| iPad / iPhone で推論が重い・熱くなる | 入力 640×480、間引き、平滑化、GPU / CPU 切替、FPS 表示で実機調整。推論は 1 顔だけ |
| iOS の GPU 実行で結果が壊れる | 設定で CPU に切替。起動時に数フレームで点の分散を見て異常なら自動で CPU にする案も |
| 手やブラシで顔が隠れて点がブレる・消える | 直前の結果を 0.5 秒保持、EMA 平滑化、隠れている側だけ薄く表示 |
| 照明や肌色で塗りの見え方が変わる | 「めやす」の表記、つよさスライダー、`multiply` 合成で肌色に馴染ませる |
| 鏡像で左右が混乱する | 常に鏡像、文言は「あなたの みぎ」、矢印は両側に出す |
| プライバシーの不安 | 端末内処理・保存なし・通信なしを「はじめに」で明記。退出時と裏に回ったときにカメラを止める |
| 既存ゲームの初回表示が遅くなる | `React.lazy` で別チャンク。tasks-vision の JS は 156KB、wasm とモデルは開いたときだけ取得 |
| 既存ユーザーの保存データ | 新しい接頭辞 `makeup_` だけを使う |
| 化粧の内容の正しさ（監修なし） | 一般的な手順に限定し「めやす」と明記。レシピは JSON なので後から差し替えやすい |
| `ctx.filter` が無い iOS 17 以前 | レイヤーごとの canvas ＋ CSS `filter: blur()` にフォールバック |
| 自動テストで顔が必要 | 偽カメラ（Chromium の `--use-fake-device-for-media-stream`）は許可フローと「顔なし」状態の確認に使い、顔のあるテストはしゃしんモードで行う。テスト用の顔写真は §13 の 9 |

## 12. 作業量の目安

- フェーズ 0: 小（1 回の作業。実機確認待ちが主）
- フェーズ 1: 中（顔認識の組み込みと性能調整。2 回に分けて push）
- フェーズ 2: 中〜大（領域の調整と描画。2〜3 回に分けて push）
- フェーズ 3: 中〜大（レシピと矢印の表現。実機で化粧しながらの確認が要る。2〜3 回）

- フェーズ 5: 小〜中

## 13. 壁打ち事項（決めてほしいこと）

優先度の高い順に並べています。各項目に私のおすすめを書いてあるので、「おすすめでよい」の一言でも進められます。

1. **誰のためのアプリか（文言の調子）**
   本番は「自分で化粧をする人（大人・中高生）」向けと理解しました。試作の文言は、共通ボタンはひらがな（あそびひろばの調子）、メイク用語はカタカナ・漢字のまま、で進めてよいですか。全部ひらがなにすると「アイシャドウ」「ハイライト」の説明が長くなります。
   → おすすめ: 上記の折衷。`strings.ts` に集めて後で切り替える

2. **ホーム画面での見せ方**
   子どものプロフィールでもカードを見せますか。選択肢: (a) 全員に見せる、(b) おうちのひと設定で ON にしたときだけ見せる（既定 OFF）、(c) 大人用プロフィールだけ。プロフィールの年齢は今 3〜12 さいに制限されているので、(c) は「おとな」の選択肢を足す改修が要ります。
   → おすすめ: 試作のあいだは (a)。子どもが触って困る要素（課金・通信）は無いため。気になるなら (b)

3. **顔認識ライブラリ**
   MediaPipe（高精度・表情と頭の向きも取れる・初回 19MB）でよいですか。それとも TensorFlow.js（4MB・点だけ・遅め）を優先しますか。
   → おすすめ: MediaPipe。唇・虹彩・笑顔検出がガイドの質に直結するため

4. **オフラインの扱い**
   CLAUDE.md の「オフラインで全部遊べる」に対し、おけしょうだけは「初回はオンライン、1 回開けば以後オフライン可」の例外にしてよいですか。全部事前キャッシュすると、さがしものしか遊ばない端末にも 19MB 落とすことになります。
   → おすすめ: 例外にする（ルールに追記）

5. **モデルファイル（3.76MB）をリポジトリにコミットすること**
   ビルド時に Google のサーバーから取る方式は CI が外部依存になるので、コミットをおすすめします。リポジトリが 4MB 増えます。
   → おすすめ: コミット

6. **ホーム画面 PWA でのカメラ許可の再確認**
   iOS の既知問題で、ホーム画面から起動すると毎回カメラ許可を聞かれる可能性があります。試作のあいだは許容し、フェーズ 0 で実態を確認してから対策（Safari のタブで開く案内など）を決める、でよいですか。

7. **ためす の品質目標**
   試作は Canvas 2D のベタ塗り ＋ ぼかし（口紅・チーク・アイシャドウが「それらしく」見える程度）でよいですか。ツヤ・ラメなどの質感は WebGL が要るので将来に回します。

8. **3 モードの優先順位**
   ためす（フェーズ 2）→ おしえて（フェーズ 3）→ ていあん（フェーズ 4）の順で考えています。コンセプトの中心が「化粧がうまくいくようにサポート」なら、おしえて を先にする手もあります。どちらを先に実機で見たいですか。
   → おすすめ: ためす を先（領域の精度が目で見て分かり、おしえて の土台にもなるため）

9. **テスト用の顔写真**
   自動テスト（しゃしんモード）とレシピの調整に、顔が写った写真が 1 枚要ります。ユーザーさんかご家族の写真を使ってよいですか（リポジトリにコミットすると公開リポジトリなら誰でも見られます）。難しければ、ライセンスが明確なフリー素材を私が探して使います。
   → おすすめ: フリー素材をコミットし、ご自身の写真は手元の確認だけに使う

10. **レシピの内容**
    最初のレシピ（ナチュラル / おでかけ）の手順と文言は、私が一般的な順序（ベース → コンシーラー → 眉 → アイシャドウ → アイライン → マスカラ → チーク → ハイライト → リップ）で作ります。普段の手順や、入れてほしい・外してほしいステップがあれば教えてください。使う人の性別や年代による違い（例: メンズメイク）も最初は考慮しません。

11. **写真の保存**
    アプリ内に保存せず、共有シート / ダウンロードに渡すだけ、でよいですか。アプリ内に残したい（ビフォー / アフターを後で見返す）なら、IndexedDB に保存する画面を足します。

12. **名前**
    「おけしょう」でよいですか。他の案: 「メイクミラー」「おけしょうミラー」「メイクアップ」。

13. **向きと端末**
    縦持ちのスマホ / iPad を基本にします。iPad 横持ちは「崩れない」程度でよいですか。それとも横持ちを主に使いますか（鏡として置く使い方なら横持ちが多いかもしれません）。

14. **単体化の形（今決めなくてよい）**
    将来の単体化は、Web サイト（別リポジトリ、同じ PWA 方式）とネイティブアプリ（Capacitor で包む。カメラ許可の保持と App Store 配布のため）のどちらを想定していますか。構造は共通ですが、ネイティブ想定ならカメラ周りを早めに抽象化しておきます。
